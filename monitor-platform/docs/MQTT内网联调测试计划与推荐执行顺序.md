# MQTT 内网联调测试计划与推荐执行顺序

版本日期：2026-07-08

适用场景：暂无云平台测试环境时，在内网完成 MQTT 接管业务层的 P0/P1 生产交付验证。

## 1. 测试目标

本测试计划用于验证平台业务 API 能通过 MQTT 接管原有网关 HTTP 直连链路，并形成完整闭环：

1. 平台业务 API 创建命令记录。
2. 平台通过 EMQX 下发 `down/proxy-command`。
3. 加密网关或解密网关 MQTT Agent 接收命令。
4. 网关调用本地业务服务执行。
5. 网关通过 `up/reply` 回传 `PROCESSING` 和最终状态。
6. 平台更新命令表、事件表和业务状态。

本计划先不覆盖 EMQX TLS、账号、ACL 安全加固，只验证内网业务可交付性。

## 2. 测试环境

| 角色 | 地址 / 标识 | 说明 |
| --- | --- | --- |
| 平台 | `192.168.1.70` | `monitor-forward`，平台 MQTT 发布、回执接收、命令状态机 |
| EMQX | 内网 EMQX | 平台、发布网关、终端网关都连接同一 Broker |
| 加密/发布网关 | `publish-gateway-11`，`192.168.77.11:8092` | 接收 MQTT 命令，处理发布网关侧链路、控制、内容投递 |
| 解密/终端网关 | `terminal-gateway-12`，`192.168.77.12:8093` | 接收 MQTT 命令，处理终端控制、截图、设备协议 |

## 3. 总体推荐顺序

推荐按以下顺序执行，不建议跳过前置阶段直接测内容投递或远程升级。

| 顺序 | 阶段 | 优先级 | 目标 | 通过后才能进入 |
| ---: | --- | --- | --- | --- |
| 0 | 基线检查 | P0 | 确认服务、DB、EMQX、时间、配置处于可测状态 | 阶段 1 |
| 1 | MQTT 连接、注册、心跳 | P0 | 证明平台和两台网关都在线 | 阶段 2 |
| 2 | 非破坏命令状态机 | P0 | 证明平台 API -> MQTT -> 网关 -> 回执 -> 表状态闭环 | 阶段 3 |
| 3 | 失败语义、超时、幂等 | P0 | 防止假成功、重复执行和状态回退 | 阶段 4 |
| 4 | `CHANGE_SYSTEM_IP dryRun` | P0 | 验证网络变更入口的非破坏闭环 | 阶段 5 |
| 5 | 链路部署 / 代理规则 | P1 | 验证 11 到 12 的业务链路配置下发 | 阶段 6 |
| 6 | 控制命令投递 | P1 | 验证亮度、黑屏、校时、查询等控制命令 | 阶段 7 |
| 7 | 内容 / 加密投递 | P1 | 验证小文件、MinIO、加密和投递状态 | 阶段 8 |
| 8 | 截图 / 状态采集 | P1 | 验证终端网关按需截图或状态采集 | 阶段 9 |
| 9 | 远程升级 verify-only | P1 | 验证下载、校验、回执，不执行真实替换 | 阶段 10 |
| 10 | 异常恢复和稳定性 | P1 | 验证重启、断线、重复消息、并发、超时 | 生产交付评审 |

## 4. 阶段 0：基线检查

目标：确认测试不是因为环境问题误判。

| 检查项 | 预期 |
| --- | --- |
| `monitor-forward` 健康 | `UP` |
| EMQX client | `monitor-platform-001`、`publish-gateway-11`、`terminal-gateway-12` 均 connected |
| 网关健康接口 | 11 的 `8092`、12 的 `8093` 可从各自运行环境访问 |
| 设备表 | 两台网关在线，deviceId 不重复或重复记录已标记清楚 |
| 命令表 | `device_mqtt_command` 已存在新增字段，如 `business_id`、`error_code`、`reply_payload` |
| 事件表 | `device_mqtt_command_event` 已存在 |
| 网关幂等表 | 11/12 的 `mqtt_command_record` 已初始化 |
| 时间同步 | 70、11、12 日志时间一致，误差不影响 timeout 判断 |
| MinIO | 内容投递和截图阶段前必须确认 endpoint、bucket、access key 可用 |
| UKey / 证书 | 内容加密阶段前必须确认加密服务可用 |

通过标准：

- 所有 P0 必需项为可用状态。
- 非 P0 项如果暂不可用，必须在测试记录中标明会影响哪些后续阶段。

## 5. 阶段 1：MQTT 连接、注册、心跳

目标：确认内网 MQTT 基础链路已恢复。

| 用例 | 目标 | 触发方式 | 预期 |
| --- | --- | --- | --- |
| 1.1 | 平台 MQTT client 在线 | 查看 EMQX clients | `monitor-platform-001` connected |
| 1.2 | 发布网关在线 | 查看 EMQX clients、设备表 | `publish-gateway-11` connected，设备表在线 |
| 1.3 | 终端网关在线 | 查看 EMQX clients、设备表 | `terminal-gateway-12` connected，设备表在线 |
| 1.4 | 注册消息 | 重启网关或等待周期注册 | 平台收到 `up/register` 并更新设备信息 |
| 1.5 | 心跳消息 | 等待 2 个心跳周期 | 平台收到 `up/heartbeat`，设备在线时间刷新 |

证据要求：

- EMQX client 列表截图或命令输出。
- `monitor-forward` 日志中注册/心跳记录。
- 设备表中两台网关的在线状态和更新时间。

## 6. 阶段 2：非破坏命令状态机

目标：用无副作用命令证明平台正式 API 到网关回执的闭环。

推荐顺序：

1. `QUERY_STATUS` 到 `publish-gateway-11`。
2. `QUERY_STATUS` 到 `terminal-gateway-12`。
3. `NOOP` 到 11 和 12。
4. `ECHO` 到 11 和 12。

| 验证点 | 预期 |
| --- | --- |
| 平台接口 | 返回命令 ID、messageId、最终状态 |
| 命令表 | `CREATED/PUBLISHED/PROCESSING/SUCCESS` 状态完整 |
| 事件表 | 至少记录 `CREATED`、`PUBLISHED`、`PROCESSING`、`SUCCESS` |
| 网关日志 | `QUERY_STATUS` 走 native probe，不调用 `/udp-proxy/config` |
| 回执 payload | 包含 `clientId`、`deviceId`、`serviceName`、`status`、`localHttpPort` |
| 业务语义 | 不能出现 HTTP 200 但业务 `code=500` 仍被判 `SUCCESS` |

通过标准：

- 11/12 的 `QUERY_STATUS` 均为 `SUCCESS`。
- `NOOP` 不触发本地 HTTP 回环。
- `ECHO` 回显 payload。
- 事件表和命令表状态一致。

## 7. 阶段 3：失败语义、超时、幂等

目标：先压住生产最容易误判的状态机问题。

| 用例 | 操作 | 预期 |
| --- | --- | --- |
| 3.1 业务失败判定 | 构造 action 返回 `httpStatus=200`、`success=true`、`code=500` | MQTT 最终回执为 `FAILED` |
| 3.2 HTTP 失败判定 | 构造 HTTP 4xx/5xx | MQTT 最终回执为 `FAILED` |
| 3.3 非法命令 | 下发未知 command | `REJECTED` 或 `FAILED`，错误信息明确 |
| 3.4 缺字段 | 缺少 targetIp、targetPort 或必要参数 | `FAILED`，错误信息明确 |
| 3.5 超时 | 临时阻断网关回执或调用不可达地址 | 平台命令状态变为 `TIMEOUT` |
| 3.6 重复 messageId | 重复下发同一 messageId | 网关不重复执行业务副作用 |
| 3.7 网关重启后重复 messageId | 首次执行后重启网关，再重复同一 messageId | DB 幂等仍然生效 |
| 3.8 状态不回退 | 已 `SUCCESS/FAILED` 后收到迟到 `PROCESSING` | 平台状态不回退 |

通过标准：

- 没有“假成功”。
- 错误原因能从平台接口、命令表、事件表、网关日志中定位。
- 重复消息不会重复写规则、重复改配置或重复执行控制。

## 8. 阶段 4：`CHANGE_SYSTEM_IP dryRun`

目标：验证网络变更业务入口已通过 MQTT 接管，同时保证不发生真实网络变更。

推荐顺序：

1. 11 执行 `dryRun=true`。
2. 12 执行 `dryRun=true`。
3. 11 执行非法参数 dry-run。
4. 12 执行非法参数 dry-run。
5. 可选：安全开关关闭时执行 `dryRun=false`，确认被拒绝。

通过标准：

| 验证点 | 预期 |
| --- | --- |
| MQTT 链路 | 平台命令进入 `SUCCESS` 或明确 `FAILED/REJECTED` |
| dry-run 成功语义 | 不执行真实 `ip addr`、`ip route`、网卡变更命令 |
| 返回字段 | 包含 `dryRun=true`、目标网卡、计划命令或计划结果 |
| 安全开关 | `dryRun=true` 不因真实变更开关关闭而失败 |
| DB 副作用 | 不触发设备表 IP 和链路节点 IP 回写 |
| 非 dry-run | 安全开关关闭时必须拒绝真实变更 |

## 9. 阶段 5：链路部署 / 代理规则

目标：验证平台链路配置通过 MQTT 下发到发布网关，并能配置 11 到 12 的代理规则。

前置：

- `192.168.77.11 -> 192.168.77.12:8093` 可达。
- 11 的网关数据库已有代理规则表。
- 12 的 `/udp-proxy/config` 或相关配置接口可用。

推荐顺序：

1. 创建最小链路，只包含 11 到 12。
2. 平台业务 API 触发 `CHAIN_DEPLOY`。
3. 验证 11 本地规则写入。
4. 验证 11 转发到 12 的配置成功。
5. 验证重复部署幂等。
6. 验证错误目标地址时返回 `FAILED`。

通过标准：

- 平台不直接访问网关 HTTP。
- 11 规则表存在对应记录。
- 11 能访问 12 的 `8093`。
- 平台命令最终 `SUCCESS`。
- 失败时能定位到发布网关、终端网关或网络哪一段。

## 10. 阶段 6：控制命令投递

目标：验证平台控制业务通过 MQTT 下发，网关执行控制服务并回传真实结果。

推荐顺序：

1. `QUERY_STATUS` 控制类查询。
2. 亮度设置，例如 `BRIGHTNESS`。
3. 黑屏开关，例如 `BLACKOUT`。
4. 校时，例如 `TIME_SYNC` 或 `NTP_SET`。
5. 非法参数测试。
6. 终端执行失败测试。

关键验收点：

| 验证点 | 预期 |
| --- | --- |
| 发布网关路径 | 平台到 11 时走 `/api/secure-delivery/control-tasks` 或对应 native handler |
| 终端网关路径 | 如支持直达 12，必须满足 `/api/secure-command/control` 的加密载荷契约 |
| 异步状态 | 不能把 `ACCEPTED` 误判为最终 `SUCCESS` |
| 最终结果 | 只有终端控制任务成功才上报 MQTT `SUCCESS` |
| 失败结果 | 终端拒绝、超时、参数错误必须上报 `FAILED` |

通过标准：

- 至少 1 个无破坏控制命令成功。
- 至少 1 个非法参数用例失败且错误信息明确。
- 命令表、事件表、网关日志三方状态一致。

## 11. 阶段 7：内容 / 加密投递

目标：验证小文件内容投递从平台业务任务到发布网关、再到终端网关的闭环。

推荐顺序：

1. MinIO 连接验证。
2. UKey / 证书 / 加密服务健康验证。
3. 小文件成功投递。
4. MinIO 文件不存在。
5. SHA256 不匹配。
6. 终端网关不可达。
7. 重复任务幂等。

通过标准：

| 验证点 | 预期 |
| --- | --- |
| 任务创建 | 平台和发布网关都能查到任务 ID |
| 文件下载 | 成功下载测试素材 |
| 校验 | SHA256 校验通过 |
| 加密 | 加密服务成功，失败时原因明确 |
| 终端投递 | 12 接收并解析安全信封 |
| 状态回传 | 平台能看到 `PROCESSING` 到最终 `SUCCESS/FAILED` |

## 12. 阶段 8：截图 / 状态采集

目标：验证终端网关按需截图或状态采集。

推荐顺序：

1. 修复或确认 12 的 MinIO 配置。
2. 确认存在可采集的规则或终端设备。
3. 下发 `SNAPSHOT_REPORT`。
4. 验证 object key、report URL、ruleId、deviceId。
5. 测试 MinIO 不可用或无规则的失败路径。

通过标准：

- 成功用例能返回可定位的截图对象。
- 失败用例不能假成功。
- 平台命令状态和终端日志一致。

## 13. 阶段 9：远程升级 verify-only

目标：验证升级通道，不执行真实生产替换。

推荐顺序：

1. 准备小型测试包和 SHA256。
2. 下发 verify-only 升级任务到 11。
3. 下发 verify-only 升级任务到 12。
4. 测试 SHA256 错误。
5. 测试下载地址不可达。
6. 可选：启用 harmless 测试脚本，不替换真实镜像。

通过标准：

- 下载、校验、状态回执均可见。
- 失败原因明确。
- 不影响当前 SSH、容器和网关运行。
- 未经单独审批不执行真实升级替换。

## 14. 阶段 10：异常恢复和稳定性

| 用例 | 操作 | 预期 |
| --- | --- | --- |
| 10.1 Broker 重启 | 重启 EMQX | 平台和网关自动重连，心跳恢复 |
| 10.2 发布网关重启 | 重启 11 容器 | 注册、心跳、订阅恢复，幂等记录保留 |
| 10.3 终端网关重启 | 重启 12 容器 | 注册、心跳、订阅恢复，幂等记录保留 |
| 10.4 平台重启 | 重启 `monitor-forward` | 订阅恢复，后续回执能处理 |
| 10.5 并发命令 | 同时下发 10 到 50 条非破坏命令 | 状态不串扰，无明显堆积 |
| 10.6 重复消息 | 重放同一 messageId | 不重复业务副作用 |
| 10.7 乱序回执 | 人工构造迟到 `PROCESSING` | 状态不回退 |
| 10.8 网关离线 | 停掉某一网关后下发命令 | 平台最终 `TIMEOUT` 或 `FAILED` |

通过标准：

- 服务恢复后无需人工重新订阅。
- 平台状态机不乱序、不回退。
- 失败场景可定位，不出现无原因失败。

## 15. 生产交付退出标准

P0 必须全部通过：

- 11/12 MQTT 在线、注册、心跳正常。
- `QUERY_STATUS`、`NOOP`、`ECHO` 通过。
- 命令表和事件表状态完整。
- 业务 `code != 200`、HTTP 非 2xx、`success=false` 均不会误判成功。
- 超时、重复 messageId、状态不回退通过。
- `CHANGE_SYSTEM_IP dryRun` 不产生真实网络变更。

P1 建议全部通过后再生产交付：

- 链路部署 / 代理规则下发通过。
- 至少一个控制命令成功，一个非法控制命令失败可定位。
- 小文件内容投递成功，并覆盖 MinIO / SHA256 / 终端不可达失败路径。
- 截图或状态采集至少成功一次。
- 远程升级 verify-only 通过，不执行真实替换。
- EMQX、平台、11、12 重启恢复通过。
