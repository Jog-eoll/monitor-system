# 青松 JetFileII UDP 文件分包重组原理

## 1. 范围与结论

本文只说明青松 JetFileII / Sigma 协议层如何把多个 UDP 报文中的文件数据重组为完整文件。

不讨论：

1. IP 层 UDP fragmentation。IP 分片由操作系统协议栈处理，应用层通常看不到 IP fragment offset / MF 标志。
2. 发布网关、终端网关之间的内部 `MessageHeader` 分片。
3. 客户端旁路签名、预审核、安全包拦截等项目实现逻辑。

依据：

1. `D:\广告屏相关资料\厂商\青松\JetFileII(CH).pdf`，JetFileII Ver2.9.15。
2. PDF 第 14 页说明：JetFileII 可基于 TCP/IP、UDP/IP、串口、GPS 等底层通信。
3. PDF 第 16-17 页说明第二类通信格式。
4. PDF 第 76-82、86 页说明文件写入命令的分包字段。
5. PDF 第 293 页说明文件写入相关状态码。

核心结论：

JetFileII 的“UDP 分片重组”不是网络层分片重组，而是应用层文件分包传输。发送端把一个文件切成多个 JetFileII 数据包，每个数据包作为一个 UDP payload 发送；接收端根据文件标识、文件总大小、分包大小、总包数、当前包号和数据区内容，按包号顺序写入或追加，直到总包数收齐或累计大小达到文件总大小，形成完整文件。

## 2. 第二类通信格式

JetFileII 第一类通信格式不支持分包发送；文件分包依赖第二类通信格式。

第二类通信包的基本布局如下：

| 偏移 | 长度 | 字段 | 含义 |
| --- | ---: | --- | --- |
| 0 | 2B | `SYN Code` | 发送包为 `0x55 0xA7` 普通和校验，或 `0x55 0xA3` CRC 校验 |
| 2 | 2B | `CheckSum` | 从校验字段后到数据结束的和校验或 CRC |
| 4 | 2B | `Data Len` | `Data` 字段长度，不是完整文件长度 |
| 6 | 2B | `Source Address` | 源地址 |
| 8 | 2B | `Destination Address` | 目标地址，前 1B 为 Group，后 1B 为 Unit |
| 10 | 2B | `Packet Serial` | 通信包序号，用于匹配回送包，不等同于文件分片号 |
| 12 | 1B | `Main CMD` | 大类命令 |
| 13 | 1B | `Sub CMD` | 小类命令 |
| 14 | 1B | `Arg Len` | 参数区长度，实际参数字节数为 `Arg Len * 4` |
| 15 | 1B | `Flag` | 写命令中通常表示是否需要回送，`0` 需要回送，`1` 不需要回送 |
| 16 | `4 * Arg Len` | `Arg` | 命令参数 |
| `16 + 4 * Arg Len` | `Data Len` | `Data` | 当前包携带的文件数据片段 |

回送包格式基本相同，普通和校验回送头为 `0x55 0xA8`，CRC 回送头为 `0x55 0xA4`。

需要特别区分两个“序号”：

| 字段 | 作用 |
| --- | --- |
| `Packet Serial` | 通信包流水号，用于 PC 判断回送包对应哪个请求包 |
| 文件写入参数中的“当前包” | 文件分片序号，从 `1` 开始，决定当前 `Data` 应放到完整文件的哪个位置 |

## 3. 文件写入分包字段

JetFileII 的文件写入命令属于 `Main CMD = 0x02`。不同 `Sub CMD` 写入不同类型文件，但分包字段高度一致。

| 命令 | 用途 | 文件标识 | 分包字段 |
| --- | --- | --- | --- |
| `0x0202` | 系统文件写入 | 12B 系统文件名，如 `CONFIG.SYS` | 文件总大小 4B、分包大小 2B、总包数 2B、当前包 2B、备注 2B |
| `0x0203` | 字库文件写入 | 12B 字库文件名 | 文件总大小 4B、分包大小 2B、总包数 2B、当前包 2B、备注 2B |
| `0x0204` | Text File 写入 | 分区号、蜂鸣器次数、12B Text File Label | 文件总大小 4B、分包大小 2B、总包数 2B、当前包 2B |
| `0x0205` | String File 写入 | 分区号、保留字节、12B String File Label | 文件总大小 4B、分包大小 2B、总包数 2B、当前包 2B |
| `0x0206` | Picture File 写入 | 分区号、保留字节、12B Picture File Label | 文件总大小 4B、分包大小 2B、总包数 2B、当前包 2B |
| `0x0207` | Array Picture File 写入 | 分区号、保留字节、12B Array Picture File Label | 文件总大小 4B、分包大小 2B、总包数 2B、当前包 2B |
| `0x0208` | 写文件到指定路径 | 路径和文件名，NULL 结尾，如 `D:\T\WELCOME.NMG` | 文件总大小 4B、分包大小 2B、总包数 2B、当前包 2B |
| `0x020D` | 写文件到指定路径，扩展 | 路径和文件名，NULL 结尾 | 文件总大小 4B、分包大小 2B、总包数 4B、当前包 4B |

`0x020D` 用于写入大于 64M 的文件，区别是“总包数”和“当前包”从 2B 扩展为 4B。

PDF 对这些命令明确要求：

1. 分包大小对同一个文件的所有包必须一致。
2. 当前包从 `0x01` 开始，第二包为 `0x02`，第三包为 `0x03`，依次递增。
3. 发送时包必须按从小到大顺序发送。
4. 每个包的 `Data` 字段携带当前片段的文件数据。

## 4. 接收端如何重组完整文件

接收端处理一个 JetFileII 文件写入 UDP 包时，逻辑上分为六步。

### 4.1 校验单个通信包

接收端先按第二类通信格式解析包头：

1. 检查同步头是否为 `0x55 0xA7` 或 `0x55 0xA3`。
2. 按校验方式验证 `CheckSum`。
3. 用 `Arg Len` 计算参数区长度。
4. 用 `Data Len` 确认当前包 `Data` 字段长度。
5. 如果包长度不匹配，协议状态码中有 `0x9006` 表示包长度不对。

### 4.2 识别文件传输会话

一个文件传输会话通常由以下字段共同确定：

1. 源地址和目标地址。
2. `Main CMD = 0x02`。
3. `Sub CMD`，即文件写入类型。
4. 文件名、File Label 或完整路径。
5. 文件总大小、分包大小、总包数。

同一文件的后续包应保持这些字段一致；只有“当前包”和 `Data` 内容随包变化。

### 4.3 确认当前包位置

文件分片号来自参数区中的“当前包”，不是包头里的 `Packet Serial`。

当前包号从 `1` 开始，因此当前片段在完整文件中的理论偏移为：

```text
offset = (当前包号 - 1) * 分包大小
```

由于协议要求按包号递增发送，接收端可以直接按到达顺序追加；更严谨的实现也可以按上述 offset 写入对应位置。

### 4.4 写入当前数据片段

当前 UDP payload 中的 `Data` 字段就是文件片段内容。

写入时需要满足：

1. 当前 `Data` 长度不能大于分包大小。
2. 分包大小应保持一致。
3. 当前包号应等于期望的下一个包号。

PDF 状态码中与此直接相关的错误包括：

| 状态码 | 含义 |
| --- | --- |
| `0x9013` | 文件写入时，包大小大于 1500，或数据大小多于分包大小 |
| `0x9014` | 文件写入时，没有按顺序发送数据包 |

这说明 JetFileII 标准文件写入流程更偏向“顺序接收并写入”，而不是任意乱序收包后再复杂排序。

### 4.5 判断文件完成

接收端可用两个强条件判断完整文件已经收齐：

1. `当前包 == 总包数`。
2. 累计写入字节数达到 `文件总大小`。

最后一包通常可能小于分包大小，但不能只依赖“最后一包长度小于分包大小”判断完成。因为当文件总大小刚好能被分包大小整除时，最后一包长度也可能等于分包大小；此时仍应以“总包数”和“文件总大小”为准。

### 4.6 回送状态

如果 `Flag = 0`，接收端应回送状态。文件写入成功时，PDF 说明回送状态码为 `0x9000`；其他状态码表示失败。

在 UDP 场景下，底层不保证可靠送达。JetFileII 文件写入表格本身没有在这些页面中定义完整的自动重传机制，因此工程上通常需要发送端结合回送状态、超时和重发策略保证可靠性。这一点属于上层实现策略，不是 IP 层自动重组。

## 5. 示例：3000 字节文件的分包

假设要发送一个 3000 字节文件：

| 参数 | 值 |
| --- | --- |
| 文件总大小 | 3000 |
| 分包大小 | 1024 |
| 总包数 | 3 |

发送端会构造 3 个 JetFileII 文件写入包：

| 当前包 | `Data` 长度 | 文件偏移 | 说明 |
| ---: | ---: | ---: | --- |
| 1 | 1024 | 0 | 第 1 段 |
| 2 | 1024 | 1024 | 第 2 段 |
| 3 | 952 | 2048 | 最后一段 |

接收端收到第 1 包后创建文件会话，收到第 2 包后继续追加，收到第 3 包后发现 `当前包 == 总包数` 且累计 3000 字节，文件完成。

## 6. 读文件方向的分包

读取文件是反向过程，但模式略有不同：PC 通常在读取命令参数里指定“分包大小”和“读取的包顺序号”，屏端回送该包的数据。

典型读取回送参数包含：

1. 文件大小。
2. 包序号。
3. 大文件场景下的扩展文件大小字段。
4. `Data` 字段中的当前片段数据。

因此读文件方向更像“按包号请求某一片”，不是屏端无状态地连续推送完整文件。若读取包序号超过文件尾，状态码中有 `0x9009` 表示“文件已到文件尾 / 包序号过大”。

## 7. 与抓包分析的关系

看到 UDP 抓包时，可以按以下顺序判断它是否属于 JetFileII 文件分包：

1. UDP payload 是否以 `0x55 0xA7` 或 `0x55 0xA3` 开头。
2. `Main CMD` 是否为 `0x02`。
3. `Sub CMD` 是否为文件写入类命令，如 `0x02` 到 `0x08`，或扩展 `0x0D`。
4. `Arg Len` 是否能覆盖文件总大小、分包大小、总包数、当前包、文件名或路径。
5. `Data Len` 是否等于当前文件片段长度。
6. 同一文件的“当前包”是否从 `1` 开始连续递增。
7. 累计 `Data` 字节数是否达到文件总大小。

如果抓包中的 Sigma Play 私有扩展格式没有完整暴露这些字段，就只能根据抓包字段和行为推断，不应直接把推断结果写成官方规范。对于 PDF 明确定义的 `0x0202` 到 `0x0208`、`0x020D` 文件写入命令，可以按本文字段解释。

## 8. 一句话总结

JetFileII 把完整文件拆成多个应用层数据包：包头说明这是哪个设备、哪个命令、当前 `Data` 有多长；参数区说明这是哪个文件、总大小是多少、每片多大、总共有几片、当前是第几片；数据区承载当前文件片段。接收端按当前包号顺序写入数据区，收齐总包数或累计到文件总大小后，得到完整文件。
