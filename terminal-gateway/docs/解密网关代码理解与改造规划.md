# 解密网关代码理解与改造规划

> 生成日期：2026-06-27  
> 范围：`D:/project02/terminal-gateway`、`publish-gateway` 中与解密网关 JSON 投递相关的代码  
> 约束：`gateway-device-protocol` 作为协议契约和厂商适配模块保持不变，后续开发基于该模块向上集成

## 1. 项目上下文摘要

### 1.1 技术栈

终端解密网关位于 `terminal-gateway`，是 Maven 多模块工程：

- `gateway-auth`：VAuth/UKey 认证与 SDK JNA 封装。
- `gateway-common`：公共接口和通用能力，例如 `CryptoService`。
- `gateway-crypto`：国密加解密实现，真实模式下对接 VAuth SDK。
- `gateway-device-protocol`：设备协议契约、能力定义、参数模型、厂商协议适配器。
- `gateway-device-core`：Spring 运行时，负责设备发现、设备选择、批量任务、命令执行编排。
- `gateway-udp-proxy`：终端网关主启动模块，负责 UDP/TCP 解密转发、规则管理、探测、快照等。

当前 Maven 基线：

- JDK：Java 8。
- Spring Boot：2.7.14。
- Netty：4.1.96.Final。
- MyBatis Plus：3.5.3.1。
- JSON：`fastjson2`、Jackson 均已存在于当前代码路径中。

后续改造不能引入新依赖，不能使用 Java 8 以上语法。

### 1.2 架构模式

解密网关当前是模块化单体，整体分为三条边界：

- HTTP 接口层：`controller` 包，例如 `UdpProxyConfigController`、`SecureCommandController`。
- 业务编排层：`manager`、`orchestrator`、`service`，例如 `UdpProxyRuleManager`、`PublishPackageOrchestrator`、`ControlCommandOrchestrator`。
- 基础设施/协议层：Netty 代理、VAuth 加解密、设备协议 core/protocol。

代码风格以 Spring Bean + Lombok + 显式日志为主，异常通常记录完整堆栈后转换为 `Result` 返回。新增代码应沿用这种组织方式。

### 1.3 业务边界

解密网关在端到端链路中的职责不是“平台内容上报”，而是：

1. 接收平台下发的链路配置。
2. 接收加密网关发来的密文流量或密文 JSON 包。
3. 使用 `CryptoService` 解密。
4. 对传统 UDP/TCP 流量执行 Message 重组后转发到 LED/情报板。
5. 对 JSON 控制/发布包执行设备选择、能力映射、命令编排，再通过 `gateway-device-core` 调用厂商协议。
6. 将设备响应或任务状态返回给加密网关/平台。

## 2. 当前代码结构理解

### 2.1 启动与 Bean 装配

主启动类：

- `terminal-gateway/gateway-udp-proxy/src/main/java/com/gateway/udpproxy/TerminalGatewayApplication.java`

该类使用 `@SpringBootApplication`，并通过 `@ComponentScan` 扫描终端网关、认证、加密、设备 core 等包。因此 `gateway-device-core` 中的 Controller、Service、Orchestrator 可以被主应用直接暴露和使用。

设备 core 自动装配类：

- `terminal-gateway/gateway-device-core/src/main/java/com/gateway/device/core/config/DeviceCoreAutoConfiguration.java`

关键 Bean：

- `DeviceSelectorResolver`：根据 `DeviceSelector` 从设备注册表筛选目标设备。
- `ProtocolRouter`：根据设备厂商和能力选择 `VendorProtocolAdapter`。
- `DeviceCommandExecutor`：异步执行单设备命令。
- `BatchCommandService`：批量命令入口。

这说明解密网关已经具备“JSON 指令 -> BatchCommandService -> 设备协议适配器”的运行基础。

### 2.2 平台配置入口

配置入口：

- `terminal-gateway/gateway-udp-proxy/src/main/java/com/gateway/udpproxy/controller/UdpProxyConfigController.java`

核心接口：

- `POST /udp-proxy/config`
- `PUT /udp-proxy/chain/{chainId}/status`
- `POST /udp-proxy/stop/{ruleId}`
- `GET /udp-proxy/rules/running`
- `POST /udp-proxy/send-command`

`/udp-proxy/config` 接收 `ConfigDTO` 后转换为 `UdpProxyRule`：

- `ruleId = chainId + "_terminal"`
- `sourceIp` 优先使用配置中的 `sourceIp`，否则使用 `publishGatewayIp`
- `targetIp/targetPort` 指向情报板或 LED 设备
- `decryptEnabled` 默认启用
- `protocol` 默认 `UDP`
- `manufacturer` 来自配置或 `registry.client.manufacturer`

这条路径解决的是“链路规则如何落到解密网关本地监听端口上”。

### 2.3 规则管理与代理启动

规则管理器：

- `terminal-gateway/gateway-udp-proxy/src/main/java/com/gateway/udpproxy/manager/UdpProxyRuleManager.java`

关键职责：

- 启动时加载数据库中 `ENABLED` 规则并自动启动代理。
- `addOrUpdateRule` 支持新增或更新规则。
- 根据规则协议启动：
  - `UdpProxyServer`
  - `TcpProxyServer`
  - `CatchAllTcpProxyServer`
- 支持额外 TCP/UDP 端口代理。
- 支持按规则停止、按链路切换状态。

这部分是传统转发链路的运行中枢，不应该在 JSON 改造中大改。JSON 指令通道应当尽量复用 `gateway-device-core`，不要强行塞进 UDP/TCP 代理流程。

## 3. 传统密文转发链路理解

### 3.1 UDP 转发链路

入口：

- `terminal-gateway/gateway-udp-proxy/src/main/java/com/gateway/udpproxy/forward/UdpProxyServer.java`

核心流程：

```text
发布网关 UDP 密文包
  -> UdpProxyServer.channelRead0
  -> sourceIp 白名单校验
  -> CryptoService.decrypt
  -> MessageAssembler.process
  -> 转发到情报板 targetIp:targetPort
  -> 情报板响应
  -> CryptoService.encrypt
  -> 回传发布网关
```

关键点：

- 白名单使用 `rule.sourceIp`，语义上应当是发布网关 IP，而不是原始发布客户端 IP。
- `decryptEnabled=true` 时，收到的数据先解密。
- 非 SVAC 模式下，解密后的内容会进入 `MessageAssembler`。
- SVAC 模式下，当前代码直接转发解密结果，不做 `MessageAssembler` 处理。

### 3.2 TCP 和 CatchAll 转发链路

TCP 路径：

- `terminal-gateway/gateway-udp-proxy/src/main/java/com/gateway/udpproxy/forward/TcpProxyServer.java`

CatchAll 路径：

- `terminal-gateway/gateway-udp-proxy/src/main/java/com/gateway/udpproxy/forward/CatchAllTcpProxyServer.java`

TCP 路径有帧拆包逻辑，单帧执行：

```text
[密文帧]
  -> CryptoService.decrypt
  -> MessageAssembler.process
  -> 写入情报板 TCP 连接
```

CatchAll 路径用于动态端口代理，按 `[4B 密文长度][密文块]` 拆帧，再执行解密、Message 处理和转发。

### 3.3 Message 协议重组

重组器：

- `terminal-gateway/gateway-udp-proxy/src/main/java/com/gateway/udpproxy/entity/message/MessageAssembler.java`

输入是解密后的 `Header + Body`。核心职责：

1. 解析 `MessageHeader`。
2. 判断是否分片。
3. 分片消息按 `messageId` 缓存，收齐后拼接。
4. 透传消息直接返回 Body。
5. 非透传消息根据 `encoding` 做解码，目前 UTF-8/JPEG/PNG 仍是透传占位。
6. 10 秒未收齐的分片会被清理。

`MessageHeader` 固定 20 字节，魔数为 `0xAB`，当前版本 `0x01`。该协议是发布网关和解密网关之间传统流量转发的内部封装，不能与“上报平台 JSON”混为一谈。

## 4. 加解密服务理解

公共接口：

- `terminal-gateway/gateway-common/src/main/java/com/gateway/common/service/CryptoService.java`

真实实现：

- `terminal-gateway/gateway-crypto/src/main/java/com/gateway/crypto/service/impl/CryptoServiceImpl.java`

职责：

- 初始化 VAuth SDK。
- 维护 UKey/认证状态。
- 提供 `encrypt(byte[])`、`decrypt(byte[])`。
- 支持普通国密整包加解密。
- 支持 SVAC PackData 模式。
- 认证成功后注册解密回调，用于 SDK 查询会话密钥和证书。

重要边界：

- 当前代码中 `svac-mode=true` 只是切换到 PackData 加解密 API，不等于应用层将所有业务内容转成 SVAC 视频/音频编码。
- `decrypt` 失败时上层通常丢弃请求或返回拒绝，不应透传到设备。

## 5. JSON 密文指令链路理解

当前仓库已经有一条独立于传统 UDP/TCP 流量的 JSON 指令通道。该通道更适合承载“加密网关与解密网关之间的 JSON 通信”。

### 5.1 解密网关 HTTP 密文入口

入口：

- `terminal-gateway/gateway-device-core/src/main/java/com/gateway/device/core/controller/SecureCommandController.java`

接口：

- `POST /api/secure-command/publish`
- `POST /api/secure-command/control`
- `GET /api/secure-command/control-tasks/{batchTaskId}`
- `GET /api/secure-command/health`

请求方式：

- `Content-Type: application/octet-stream`
- Body 是加密后的二进制字节，不是明文 JSON。
- Header 使用：
  - `X-Delivery-Task-Id`
  - `X-Command-Task-Id`
  - `X-Request-Id`

Controller 当前只做入口分发，真正解密和编排在 Orchestrator 中完成。

### 5.2 发布包编排

编排器：

- `terminal-gateway/gateway-device-core/src/main/java/com/gateway/device/core/orchestrator/PublishPackageOrchestrator.java`

处理流程：

```text
密文发布包
  -> CryptoService.decrypt
  -> UTF-8 JSON
  -> StandardizedPublishPackage
  -> 校验 target/files
  -> DeviceSelectorResolver 选择目标设备
  -> 可选清理媒体/播放列表
  -> 按 orderNo 上传文件
  -> 可选设置播放列表
  -> 返回 SecureCommandResponse
```

当前支持的文件类型映射：

- `IMAGE/JPG/JPEG/PNG/BMP` -> `CommonDeviceCapability.IMAGE_UPLOAD`
- `VIDEO/MP4/FLV/AVI` -> `CommonDeviceCapability.VIDEO_UPLOAD`
- `TEXT/TXT` -> `CommonDeviceCapability.TEXT_UPLOAD`
- `NMG` -> `JetFileIICapability.NMG_FILE_UPLOAD`
- `PMG` -> `JetFileIICapability.PMG_FILE_UPLOAD`
- `QST` -> `JetFileIICapability.QST_FILE_UPLOAD`

当前发布包 DTO：

- `terminal-gateway/gateway-device-core/src/main/java/com/gateway/device/core/controller/dto/StandardizedPublishPackage.java`

主要字段：

- `deliveryTaskId`
- `sigmaPublishId`
- `action`
- `target`
- `playlist`
- `files`
- `options`
- `publishPermit`

文件内容通过 `contentBase64` 内嵌在 JSON 中。解密网关解密 JSON 后再 Base64 解码为字节，构造 `TextUploadParams` 或 `MediaUploadParams`。

### 5.3 控制指令编排

编排器：

- `terminal-gateway/gateway-device-core/src/main/java/com/gateway/device/core/orchestrator/ControlCommandOrchestrator.java`

处理流程：

```text
密文控制包
  -> CryptoService.decrypt
  -> UTF-8 JSON
  -> StandardizedControlPackage
  -> command 映射为 DeviceCapability
  -> params 映射为 CommandParams
  -> DeviceSelector
  -> BatchCommandService.submit
  -> 返回 SecureControlResponse
```

当前控制命令映射：

- `BRIGHTNESS` -> `CommonDeviceCapability.BRIGHTNESS_SET`
- `REBOOT` -> `CommonDeviceCapability.POWER_CONTROL_REBOOT`
- `BLACKOUT` -> `CommonDeviceCapability.SCREEN_BLACKOUT`
- `TIME_SYNC` -> `CommonDeviceCapability.TIME_SYNC`
- `QUERY_STATUS` -> `CommonDeviceCapability.DEVICE_INFO_GET`
- `POWER` 当前未映射，代码中只提示支持 `REBOOT`

当前控制包 DTO：

- `terminal-gateway/gateway-device-core/src/main/java/com/gateway/device/core/controller/dto/StandardizedControlPackage.java`

主要字段：

- `taskId`
- `action`
- `source`
- `target`
- `command`
- `params`

### 5.4 参数映射器

参数映射器：

- `terminal-gateway/gateway-device-core/src/main/java/com/gateway/device/core/service/CommandParamsMapper.java`

职责是把外部 JSON 中的 `Map<String, Object>` 转成 `gateway-device-protocol` 中定义的 `CommandParams`。

当前已覆盖：

- 列表查询、上传、下载、删除。
- 播放列表查询/设置。
- 黑屏、颜色测试、亮度、校时。
- `NTP_SET`
- `DEVICE_IP_SET`
- `SCREEN_ATTRIBUTE_SET`
- Nova 音量、分辨率、登录。

当前缺口：

- `FONTS_SYNC`、`FONTS_GET` 还没有完整对外命令映射。
- `AP_NETWORK_SWITCH` 还没有从 JSON 控制命令映射到 `NovaViplexCoreCapability.AP_NETWORK_SWITCH`。
- `bytesValue` 只接受 `byte[]`，如果外部 JSON 直接传 Base64 字符串，当前不会自动解码。
- 控制指令白名单和解密网关映射不完全一致，需要和发布网关统一。

## 6. 发布网关侧 JSON 投递理解

### 6.1 发布任务投递

发布网关实现：

- `publish-gateway/gateway-udp-proxy/src/main/java/com/publishgateway/udpproxy/service/impl/SecureDeliveryServiceImpl.java`

核心流程：

```text
安全发布任务
  -> 验证 publishPermit
  -> 下载文件
  -> 校验 hash
  -> 构建 StandardizedPublishPackage
  -> JSON 序列化
  -> CryptoService.encrypt
  -> HTTP POST /api/secure-command/publish
  -> 解析解密网关响应
```

这条链路说明“加密网关和解密网关之间的 JSON 通信”已经不是设想，而是有基础实现。问题在于契约还不够稳定，需要补 schema、幂等、响应语义和能力映射。

### 6.2 控制任务投递

发布网关实现：

- `publish-gateway/gateway-udp-proxy/src/main/java/com/publishgateway/udpproxy/service/impl/ControlDeliveryServiceImpl.java`

核心流程：

```text
外部控制任务密文包
  -> 发布网关解密并校验
  -> 构建标准控制 JSON
  -> CryptoService.encrypt
  -> HTTP POST /api/secure-command/control
  -> 保存 batchTaskId / mappedCapability
  -> 后续轮询 /api/secure-command/control-tasks/{batchTaskId}
```

当前发布网关控制命令白名单包含：

- `BRIGHTNESS`
- `POWER`
- `BLACKOUT`
- `TIME_SYNC`
- `QUERY_STATUS`
- `REBOOT`

但解密网关侧 `POWER` 尚未映射成功，因此存在“发布网关允许，解密网关拒绝”的契约不一致。

## 7. `gateway-device-protocol` 的约束和正确用法

协议文档 V2 明确：

- `gateway-device-protocol` 是接口契约、数据模型、厂商适配器、参数类。
- `gateway-device-core` 是 Spring 运行时，提供发现、命令执行、事件、传输层。
- 消费方应通过 `BatchCommandService`、`DeviceSelector`、`CommonDeviceCapability` 等入口使用。

因此本次解密网关改造的正确边界是：

- 不修改 `gateway-device-protocol`。
- 在 `gateway-device-core` 增加 JSON 契约适配、校验、命令映射和编排。
- 在 `gateway-udp-proxy` 保持传统代理逻辑稳定，只补必要配置、日志或健康检查。
- 在 `publish-gateway` 做最小配套，保证发出的 JSON 与解密网关镜像 DTO 一致。

## 8. 当前主要问题清单

### P1：JSON 契约没有统一 envelope

当前发布包和控制包是两个独立 DTO，缺少统一字段：

- `schemaVersion`
- `messageType`
- `requestId`
- `timestamp`
- `sourceGatewayId`
- `signature/hash`

后果是后续扩展命令时容易继续堆字段，发布网关和解密网关两侧难以做版本兼容。

### P1：控制命令白名单与解密侧映射不一致

发布网关允许 `POWER`，但解密网关 `ControlCommandOrchestrator` 当前没有映射 `POWER` 到可执行能力，只提示当前支持 `REBOOT`。

建议短期处理：

- 要么发布网关移除 `POWER`。
- 要么解密网关明确支持 `POWER_ON/POWER_OFF`，但前提是 `gateway-device-protocol` 已有可用能力和厂商 Handler。

在不修改 protocol 的约束下，短期不建议硬做 `POWER`。

### P1：文档 V2 新增能力没有全部接到 JSON 控制入口

文档 V2 提到：

- `FONTS_SYNC`
- `FONTS_GET`
- `AP_NETWORK_SWITCH`
- `NTP_SET`
- `DEVICE_IP_SET`
- `SCREEN_ATTRIBUTE_SET`

其中 `NTP_SET`、`DEVICE_IP_SET`、`SCREEN_ATTRIBUTE_SET` 在 `CommandParamsMapper` 已有参数转换，但 `ControlCommandOrchestrator` 尚未暴露对应 command 映射。

`FONTS_SYNC`、`FONTS_GET`、`AP_NETWORK_SWITCH` 也需要补完整 command -> capability -> params 的链路。

### P1：发布/控制响应语义需要稳定

发布网关侧会解析解密网关响应中的：

- `code`
- `data.accepted`
- `data.status`
- `data.message`
- `data.steps`
- `data.batchTaskId`
- `data.mappedCapability`

解密网关必须固定这些字段，不能因为发布和控制两条链路返回结构不同导致发布网关误判。

### P2：Base64 字节参数转换不完整

`PublishPackageOrchestrator` 中 `contentBase64` 会被直接 Base64 解码，因此发布包路径可用。

但 `CommandParamsMapper.bytesValue()` 目前只接受 `byte[]`。如果后续控制 JSON 或通用 batch JSON 中使用 Base64 字符串传 `data`，当前不会自动转字节。

建议扩展为同时支持：

- `byte[]`
- Base64 字符串
- `List<Number>` 字节数组形式

### P2：幂等和重复投递防护不足

当前 `requestId`、`deliveryTaskId`、`commandTaskId` 主要用于日志和任务 ID，没有统一去重缓存。

建议在解密网关新增短期幂等缓存：

- key：`requestId` 或 `deliveryTaskId/commandTaskId`
- value：响应摘要
- TTL：例如 10 到 30 分钟

避免加密网关 HTTP 超时重试时重复下发设备命令。

## 9. 推荐改造方案

### 9.1 第一阶段：稳住 JSON 通信契约

改造位置：

- `gateway-device-core/controller/dto`
- `gateway-device-core/controller/SecureCommandController.java`
- `gateway-device-core/orchestrator`
- `publish-gateway/gateway-udp-proxy/service/impl/SecureDeliveryServiceImpl.java`
- `publish-gateway/gateway-udp-proxy/service/impl/ControlDeliveryServiceImpl.java`

新增或调整：

1. 新增统一 envelope DTO，例如 `SecureGatewayEnvelope`。
2. 新增统一响应 DTO，例如 `SecureGatewayAck`。
3. Controller 层统一校验：
   - body 非空。
   - 最大 payload 大小。
   - Header 和 JSON 内任务 ID 一致。
4. Orchestrator 层统一：
   - 解密失败返回 `DECRYPT_FAILED`。
   - JSON 解析失败返回 `BAD_JSON`。
   - 参数校验失败返回 `VALIDATION_FAILED`。
   - 无设备返回 `TARGET_NOT_FOUND`。
   - 能力不支持返回 `UNSUPPORTED_CAPABILITY`。

兼容策略：

- 保留旧 `StandardizedPublishPackage` 和 `StandardizedControlPackage`。
- 若解密后 JSON 没有 `schemaVersion/messageType`，按旧 DTO 解析。
- 若有 envelope，则按新契约解析。

### 9.2 第二阶段：补齐 V2 能力映射

改造位置：

- `ControlCommandOrchestrator`
- `CommandParamsMapper`

建议新增 command：

| 外部 command | 内部 capability | 参数类型 | 说明 |
|---|---|---|---|
| `BRIGHTNESS` | `CommonDeviceCapability.BRIGHTNESS_SET` | `BrightnessSetParams` | 已有，需保留 |
| `REBOOT` | `CommonDeviceCapability.POWER_CONTROL_REBOOT` | `EmptyParams` | 已有，需保留 |
| `BLACKOUT` | `CommonDeviceCapability.SCREEN_BLACKOUT` | `ScreenBlackoutParams` | 已有，需保留 |
| `TIME_SYNC` | `CommonDeviceCapability.TIME_SYNC` | `TimeSyncParams` | 已有，需保留 |
| `QUERY_STATUS` | `CommonDeviceCapability.DEVICE_INFO_GET` | `EmptyParams` | 已有，需保留 |
| `NTP_SET` | `CommonDeviceCapability.NTP_SET` | `NtpSetParams` | 补 orchestrator 映射 |
| `DEVICE_IP_SET` | `CommonDeviceCapability.DEVICE_IP_SET` | `IpConfigParams` | 补 orchestrator 映射 |
| `SCREEN_ATTRIBUTE_SET` | `CommonDeviceCapability.SCREEN_ATTRIBUTE_SET` | `ScreenAttributeParams` | 补 orchestrator 映射 |
| `FONTS_GET` | `CommonDeviceCapability.FONTS_GET` | `EmptyParams` | 补完整链路 |
| `FONTS_SYNC` | `CommonDeviceCapability.FONTS_SYNC` | `FontSyncParams` | 补 params 映射 |
| `AP_NETWORK_SWITCH` | `NovaViplexCoreCapability.AP_NETWORK_SWITCH` | `ApNetworkSwitchParams` | 补 Nova 私有能力映射 |

不建议短期支持：

- `POWER`，除非先确认 protocol/core 中已有明确开关机能力并且对应厂商 Handler 可用。

### 9.3 第三阶段：任务状态和可观测性

当前控制任务已有查询接口：

- `GET /api/secure-command/control-tasks/{batchTaskId}`

建议补发布任务查询：

- `GET /api/secure-command/publish-tasks/{orchestrationTaskId}`

日志建议统一打印：

- `requestId`
- `deliveryTaskId`
- `commandTaskId`
- `chainId`
- `target.deviceId/ip/vendor`
- `mappedCapability`
- `batchTaskId`
- 解密前后 payload 长度，禁止打印明文敏感内容

### 9.4 第四阶段：传统链路保持兼容

不要把 JSON 指令强行塞入 `MessageAssembler`。

原因：

- `MessageAssembler` 面向传统 UDP/TCP 转发，输入是解密后的内部二进制 Message。
- JSON 指令是 HTTP 密文包，解密后是应用层 JSON。
- 两条链路的报文类型、重试方式、响应语义不同。

推荐边界：

- 传统发布软件原始流量继续走 UDP/TCP 密文转发。
- 结构化发布/控制任务走 `/api/secure-command/*`。

## 12. 总结

解密网关当前已经同时具备两类能力：

1. 传统 UDP/TCP 密文转发能力：适合透明代理发布软件原始流量。
2. HTTP JSON 密文指令能力：适合加密网关和解密网关之间进行结构化发布、控制、查询。

本次改造不应重写 `gateway-device-protocol`，也不应破坏传统 Message 转发链路。最高可行性的方案是：保留现有 UDP/TCP 解密转发；以 `SecureCommandController`、`PublishPackageOrchestrator`、`ControlCommandOrchestrator`、`CommandParamsMapper` 为核心，把 JSON 契约、能力映射、幂等和响应语义补齐，使发布网关和解密网关之间的 JSON 通信稳定、可扩展、可联调。
